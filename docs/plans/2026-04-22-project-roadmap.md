# 穿书模拟器项目路线图

## 目标

把当前“README + HTML 原型”状态，推进到可持续扩写的微信小游戏项目。

## 当前状态

当前项目已有：

- 产品方向说明与协作规则
- 一个可在微信开发者工具中运行的宫斗本首册
- 数据结构、运行时、基础 UI、校验脚本
- 剧情写作模板与检查表

当前项目还缺：

- 剧本细节持续打磨
- 交互细节与反馈节奏优化
- 分享图与分享结果页设计
- 过程中的人物或事件形象图方案
- 第二题材模板与扩书流程

## 开发分期

## Phase 0 规划固化

目标：

- 把脑暴结果沉淀成项目文档
- 明确故事系统、第一册蓝图、skill 机制、实施路线

交付物：

- Story System v1
- 宫斗本第一册蓝图
- Story Skill 工作流
- 项目路线图

状态：

- 已完成

## Phase 1 数据结构与内容底稿

目标：

- 把 Story System v1 转成真实数据 schema
- 产出第一册的节点列表与分支图

建议产出：

- `js/data/schema.js` 或等价定义
- `js/data/books/palace-book-01.js`
- 节点 ID 规范
- 结局定义
- 条件表达式解释器

验收标准：

- 能用代码读取并遍历 Book 数据
- 能判断当前节点有哪些可见选项
- 能根据权重抽取下一节点

状态：

- 已完成

## Phase 2 HTML 原型升级验证

目标：

- 不急着上微信小游戏，先在 HTML 原型里验证新数据结构

建议产出：

- 原型页改为从数据结构驱动
- 支持条件文本
- 支持条件选项
- 支持概率结果
- 支持基础结局数据化

验收标准：

- 第一册至少一条完整路线可跑通
- 关键选择在后文能看到回响
- 随机事件能正常触发且不混乱

状态：

- 已由小游戏首册直接承接，不再作为独立阶段推进

## Phase 3 微信小游戏骨架

目标：

- 把已经验证过的玩法迁移到小游戏工程

建议产出：

- `game.js`
- `game.json`
- `project.config.json`
- `js/renderer/`
- `js/runtime/`
- `js/data/`

关键任务：

- Canvas 文本排版
- 按钮布局与点击检测
- 页面滚动或分页
- 场景状态机
- 数据驱动渲染

验收标准：

- 小游戏开发者工具内可稳定跑通首册主流程

状态：

- 已完成基础版本，当前进入持续打磨阶段

## Phase 4 质量工具与扩书准备

目标：

- 降低第二本、第三本的制作成本

建议产出：

- 离线剧情校验脚本
- 路径模拟脚本
- 题材模板
- 文案编写模板

验收标准：

- 新增一本题材时，不需要重写底层结构
- 能在写故事前就发现明显结构问题

状态：

- 部分完成，持续推进

## 当前优先级 backlog

### P0

- 持续打磨宫斗本首册的剧本细节
- 持续打磨交互反馈与分支体感
- 设计正反馈、爽点与分享欲的实现方式
- 设计分享图信息结构与视觉方向
- 设计过程中的人物或事件形象图策略
- 保持核心说明文档、路线图、迭代日志同步

### P1

- 调整评分分布与结局展示体验
- 增强不同路线的可感知差异
- 把过程中的视觉插图和当前文字节奏结合起来

### P2

- 实现分享结果页与分享图导出
- 打磨结果页、标签、金句、路线总结
- 为后续题材扩展准备视觉与数据模板

### P3

- 第二题材模板
- 角色/事件视觉素材工作流
- 更细的剧情校验与体验校验工具

## 建议工作顺序

你不在的时候，我建议按下面的节奏推进最稳。

1. 完成规划文档
2. 细化第一册节点清单
3. 再进入数据结构实现
4. 再做 HTML 验证
5. 最后迁移到微信小游戏

## 风险清单

### 内容风险

- 分支写太多导致不可维护
- 选项有数值变化但无叙事意义
- 结局只是改名，没有真实路线感
- 剧情虽然能跑通，但爽点和正反馈不足
- 分享结果不够有传播感

### 技术风险

- 条件系统写得太复杂，后续难填内容
- 渲染系统先做太早，反而拖慢故事结构验证
- 插图与分享图加入后，布局和资源管理复杂度上升

### 流程风险

- 每次讨论有新原则，但没沉淀下来
- 不同题材开始后，规则互相污染
- 换工具或换 AI 时，项目状态不同步

## 当前建议的下一步

当前最值得做的是：

1. 继续打磨宫斗本首册的剧本与交互细节
2. 把正反馈、爽点、分享欲、分享图、过程形象图正式纳入产品方案
3. 让项目说明、路线图、迭代日志持续保持同步
